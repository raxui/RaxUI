# دليل أدوات الفحص المحلي — SheenUI

العربية | [English](local-checks.md)

هذا الملف مخصّص لفحص **مستودع المكتبة نفسه** أثناء التطوير وقبل الدمج.
لتثبيت المكتبة داخل تطبيق مستهلك، راجع [دليل الاستخدام المحلي](local-development.ar.md).

## تجهيز البيئة أول مرة

استخدم PowerShell على Windows 11، وتأكد من وجود:

- Node.js 22 أو أحدث، مع npm.
- .NET SDK 10 لبناء المستودع.
- أدوات .NET 8 و9 ومتطلبات تشغيلهما لاختبارات تطبيقات Blazor الكاملة.
- PowerShell 7؛ اسم أمره `pwsh`.
- اتصال بالإنترنت لاستعادة الاعتماديات وتنزيل المتصفح وتطبيقات الاختبار.

```powershell
node --version
npm --version
dotnet --list-sdks
dotnet --list-runtimes
pwsh --version
```

انتقل إلى جذر المستودع الذي يحتوي `package.json` و`SheenUI.slnx`:

```powershell
cd C:\Users\saada\source\repos\SheenUI
npm ci
```

إذا بقي مجلد نسختك المحلية باسم `BlazorUI`، فاستخدم مساره الفعلي.
أعد تشغيل `npm ci` عند تغيّر الاعتماديات أو ملف `package-lock.json`.
لا يلزم تشغيل الطرفية كمسؤول لمجرد استخدام أدوات الفحص.

## الأوامر الأساسية

### الفحص السريع أثناء التطوير

```powershell
npm run check
```

استخدمه بعد التعديلات اليومية. يتحقق من الأنماط والأنواع والاختبارات وبناء
.NET والتنسيق، ويستثني اختبارات المتصفح لتطبيقات Blazor.

### الفحص الكامل قبل الدمج

```powershell
npm run check:full
```

استخدمه على النسخة التي تنوي دمجها. يشمل الفحص السريع بالإضافة إلى إنشاء
تطبيقات حقيقية وتشغيل اختبارات المتصفح، وتجهيز حزمة .NET محلياً.
في التجربة المحلية السابقة استغرق السريع نحو 34 ثانية والكامل نحو 4 دقائق
ونصف؛ هذه أوقات إرشادية تتغيّر حسب الجهاز والشبكة والكاش.

## ما الذي يفحصه كل أمر؟

| الفحص | السريع | الكامل |
| --- | --- | --- |
| مطابقة CSS المولّد مع مصدر SCSS | نعم | نعم |
| أنواع TypeScript | نعم | نعم |
| اختبارات React والأداة وRegistry وبصمات الملفات | نعم | نعم |
| بناء أداة .NET للأطر 8 و9 و10 | نعم | نعم |
| تنسيق C# | نعم | نعم |
| اختبارات .NET التي لا تتطلب متصفحاً | نعم | نعم |
| تطبيقات Blazor حقيقية على .NET 8 و9 و10 | لا | نعم |
| إنشاء حزمة NuGet محلية | لا | نعم |
| تطبيقات Vite عبر create-vite 6.5.0 و7.1.3 و9.3.1 | لا | نعم |
| تطبيقات Next.js 15.5.28 و16.4.3 | لا | نعم |
| التحقق من أخطاء المسافات في الفروق غير المرحّلة إلى Git | نعم | نعم |

اختبارات القبول تعمل بالتتابع لأن كلاً منها يحزم أداة React من المصدر نفسه.
رقم `create-vite` هو إصدار أداة إنشاء التطبيق، وليس بالضرورة رقم Vite الناتج.

## قراءة النتيجة

كل مرحلة تبدأ بسطر مثل:

```text
[check] TypeScript
```

النجاح الكامل ينتهي بسطر بهذا الشكل، مع زمن التنفيذ الفعلي:

```text
[check] PASS (full, 270s). Nothing was published.
```

عند فشل مرحلة يتوقف الأمر قبل المراحل التالية، ويظهر عادةً:

```text
[check] FAILED: TypeScript
```

لفحص رمز الخروج، نفّذ هذا مباشرة بعد أمر الفحص في PowerShell:

```powershell
$LASTEXITCODE
```

- `0`: اكتمل الفحص بنجاح.
- قيمة غير صفرية: فشل الفحص أو تعذّر تشغيل مرحلة؛ راجع أول خطأ.
- `2` عند تمرير خيارات غير مدعومة: خطأ في طريقة استدعاء أداة الفحص.

نجاح بعض الاختبارات لا يعني نجاح الأمر كله. الاختبار المتخطّى ليس اختباراً
ناجحاً؛ سجّل عدد الاختبارات المتخطّاة وسببها عند توثيق النتيجة.

## عند فشل الفحص

| المرحلة أو الرسالة | الإجراء |
| --- | --- |
| `Install the repository dependencies first` | شغّل `npm ci` من جذر المستودع. |
| `Shared CSS is current` | أعد توليد CSS باستخدام `npm run theme:css`، ثم حدّث البصمات المتأثرة وراجع الفروق قبل إعادة الفحص. |
| TypeScript أو اختبارات React | أصلح الخطأ الظاهر في الملفات المحددة، ثم أعد الفحص المناسب. |
| بناء .NET | تحقق من SDK المطلوب، والاستعادة، وأخطاء C# أو Razor. |
| تنسيق C# | شغّل `dotnet format SheenUI.slnx` وراجع تعديلاته، ثم أعد الفحص. |
| `pwsh` غير موجود | ثبّت PowerShell 7 وأعد فتح الطرفية. |
| تعذّر تنزيل Chromium أو اعتماديات تطبيق تجريبي | تحقق من الاتصال بالشبكة والوكيل وصلاحيات الكاش؛ لا تعتبر ذلك نجاحاً للاختبارات. |
| `Diff whitespace` | راجع نتيجة `git diff --check` وأصلح المسافات أو الأسطر التي يحددها. |

الفحص السريع أيضاً قد يحتاج الشبكة عند أول استعادة لاعتماديات .NET؛ وجوده
محلياً لا يعني أنه يعمل دون إنترنت في بيئة لم تُجهّز مسبقاً.

لتحديث بصمات ملفات React بعد تعديل مصدر الثيم أو المكونات:

```powershell
node src/react-cli/scripts/update-hashes.mjs
```

أما بصمات أصول Blazor فراجعها في ملفات manifest المقابلة. تحديث البصمة لا
يغني عن مراجعة التغيير واختباره.

## إعادة مرحلة محددة أثناء الإصلاح

يمكن تشغيل هذه الأوامر لعزل المشكلة من جذر المستودع:

```powershell
npm run typecheck
npm test
dotnet build SheenUI.slnx -c Release
dotnet format SheenUI.slnx --verify-no-changes --no-restore
dotnet test SheenUI.slnx -c Release --no-build
npm run test:acceptance
npm run test:acceptance:next
```

ابنِ الكود بعد تغييره قبل استخدام `dotnet test --no-build` حتى لا تختبر نواتج
بناء قديمة. أوامر القبول المنفردة لا تشغّل مصفوفة الإصدارات كلها؛ الأمر
`check:full` هو الذي يختبر المصفوفة المحددة أعلاه ويجهّز Chromium.

## قبل دمج طلب التغيير

1. شغّل `npm run check:full` على التغييرات النهائية.
2. عالج أي فشل قبل الدمج.
3. أضف نتيجة الفحص وأي اختبارات متخطّاة إلى وصف PR، مثلاً:

```text
Local validation: npm run check:full — PASS
Environment: Windows 11
Skipped tests: record the actual count and reason
```

هذه آلية عمل للمطور وليست شرط دمج مفروضاً من GitHub. نجاح Windows لا يثبت
التوافق مع Linux؛ نتحقق من Linux أيضاً قبل النشر العام.

## الملفات الناتجة وعلاقة GitHub

- البناء والحزم ناتجة محلياً، ومنها `bin/` و`obj/` و`nupkg/`.
- تطبيقات القبول مؤقتة، وتنزيلات Chromium تبقى في كاش Playwright المعتاد.
- لا يحدّث الفحص تطبيقاتك المستهلكة، ولا ينشر على npm أو NuGet.
- تنفيذ الأوامر المحلية لا يستهلك دقائق GitHub Actions.
- بعد دمج إعداد التشغيل اليدوي، يمكن تشغيل CI اختيارياً من
  **Actions → CI → Run workflow**؛ ذلك التشغيل يستهلك حصة GitHub المعتادة.
- نتائج GitHub الحمراء القديمة لا تتغيّر تلقائياً عند نجاح الفحص المحلي.

مصدر الأوامر: [scripts/check.mjs](../scripts/check.mjs)، وتعريفاتها في
[package.json](../package.json).
