# ADR 001 — Hybrid CSS

- **Status:** Accepted; component styling superseded by [ADR 007](007-blazor-shared-theme.md): themed Blazor components get their styles from the shared `sheenui.css`, not `.razor.css` isolation. The load order and `init` link rules below still apply.
- **Date:** 2026-10-23

## Context

Installed components are copied into the consumer project as editable source. Their styles must load reliably in every supported Blazor project without a Sass build and without the CLI managing one stylesheet link per component.

Two models were considered for component styles: plain global CSS files installed at stable paths, and Blazor CSS isolation through `.razor.css` files. Shared concerns (Bootstrap, design tokens, themes) are global by nature.

## Decision

Use a hybrid model:

- Bootstrap CSS is global and provides layout and utilities.
- `tokens.css` and `themes.css` are global and define the customization variables and themes.
- Each component ships a matching `.razor.css` file copied next to its `.razor` file. Blazor bundles it into the application's generated `{AssemblyName}.styles.css` during the consumer build.

The supported host loads styles in this order:

1. Bootstrap
2. `tokens.css`
3. `themes.css`
4. `{AssemblyName}.styles.css`
5. Explicit consumer overrides

`init` adds each required link exactly once in `Components/App.razor`. It preserves unrelated links, detects an existing Bootstrap reference before adding another, and verifies the styles bundle reference using the evaluated assembly name. Ambiguous custom host markup produces actionable instructions instead of a speculative rewrite.

The CLI never links individual `.razor.css` files and never modifies generated bundles.

CSS variables and component parameters are the primary customization API. Source order does not override specificity.

## Alternatives Considered

- **Plain global CSS per component:** Requires the CLI to add and remove one link per component or maintain an aggregate stylesheet. More host edits, more ways to drift, and styles leak globally.
- **Single aggregate stylesheet generated by the CLI:** Must be regenerated on every install, update, and removal, and conflicts with consumer edits to that file.
- **Sass:** Adds a build dependency that the consumer may not have.

## Consequences

- Adding a component needs no host stylesheet change after `init`.
- Component styles are scoped and cannot leak into unrelated markup.
- Isolation applies only to markup rendered by the component itself. Styling child content (for example `ChildContent`) requires an intentional wrapper element and `::deep`. Components that accept child content must choose this pattern deliberately.
- Consumers who rename the assembly or customize the host must keep the styles bundle reference valid; `init` verifies it.
